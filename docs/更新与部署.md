# 改代码 → 上线

## 平时怎么做

在本机改完代码，Git Bash 里跑一条：

```bash
bash tools/deploy.sh "改了什么"
```

它会依次做五件事，每步都打印进度：

1. 把改动列出来给你看，问一句确认，然后提交
2. 推到 GitHub
3. 服务器从 GitHub 拉最新代码
4. 重建 Docker 镜像并重启容器
5. 体检：核对本机和服务器的版本号一致、公网地址返回 200

**中途断了直接重跑。** 到这台 OCI 的 SSH 偶尔会掉线，五步里每一步重复执行都不会做坏事。

如果改动已经自己 `git commit` 过了，就不用带说明：

```bash
bash tools/deploy.sh
```

## 为什么必须「重建镜像」，不能只重启

`Dockerfile` 里有这么一行：

```
COPY service/ ./service/
```

`COPY` 发生在**构建镜像的时候**，是一次性复印。复印完，容器里的 `/app/service/` 和服务器硬盘上的 `/home/ubuntu/flame-demo/service/` 就是两份互不相干的文件了，只是内容碰巧一样。

所以在服务器上改 `service/` 下的文件，容器里纹丝不动 —— 必须重新复印一遍，也就是 `docker compose up -d --build`。

只有三个目录是真正「挂载」进容器的，改了立刻生效、不用重建：

| 服务器上的路径 | 容器里 | 放什么 |
|---|---|---|
| `flame-demo/static/` | `/app/static` | 生成的图片和报告页 |
| `flame-demo/data/` | `/app/data` | 台账数据库 |
| `flame-demo/inbox/` | `/app/inbox` | 补录用的原始照片（只读） |

一张对照表：

| 你改了 | 要做什么 |
|---|---|
| `service/`、`tools/`、`dify/` 里的代码 | `bash tools/deploy.sh` —— 必须重建 |
| 服务器上的 `.env` | `docker compose up -d` —— 重启就行，不用重建 |
| `static/`、`data/`、`inbox/` 里的东西 | 什么都不用做 |

`docker compose restart` 在第一种情况下**没用**：它只是把旧镜像重新跑一遍，代码还是旧的。这是最容易踩的坑 —— 命令跑成功了页面却没变，然后开始怀疑是浏览器缓存。

## 服务器上是什么结构

`/home/ubuntu/flame-demo` 是 GitHub 仓库的一份检出，加上几样不进 git 的东西：

```
flame-demo/
├── .git/            指向 github.com/chasezhang1999/boiler-flame-demo
├── service/ tools/ dify/ Dockerfile ...   跟 GitHub 一致，deploy.sh 会覆盖
├── .env             密钥，只在服务器上，不进 git
├── data/            台账数据库
├── static/          生成的图片
└── inbox/           原始照片
```

脚本第 3 步用的是 `git reset --hard`，不是 `git pull`。意思是**一切以 GitHub 为准**，服务器上的本地改动一律作废。这样就不会出现「服务器上有人手改过，pull 冲突了卡住」的局面。`.env`、`data/`、`static/`、`inbox/` 都写在 `.gitignore` 里，`reset` 碰不到。

推论：**别在服务器上直接改代码**，下次发布就没了。要改就在本机改，走上面那条流程。

## 出问题了怎么看

```bash
ssh -i ~/.ssh/oracle_sg ubuntu@140.245.117.205 'docker logs --tail 50 flame-cv'
```

确认服务器上跑的是哪个版本：

```bash
ssh -i ~/.ssh/oracle_sg ubuntu@140.245.117.205 'cd /home/ubuntu/flame-demo && git log --oneline -1'
```

跟本机 `git log --oneline -1` 对得上，就说明代码是新的。

## 一条红线

这个 GitHub 仓库是**公开**的。`.env` 里有 Dify 和模型的 key，已经写进 `.gitignore` 了，正常不会被提交。`deploy.sh` 在提交前会把文件列表打给你看并等你确认 —— **那一眼别跳过**，看到不该出现的文件就按 N。
